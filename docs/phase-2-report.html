Proposed architecture

Requests are identity-scoped; metadata and binary files are separate private resources.

Key controls

  • Explicit database grants and row-level security.
  • Private bucket with owner-scoped Storage policies.
  • Server-side file validation, generated keys and quotas.
  • Short-lived access links; never log bearer URLs.
  • Separate recovery plans for database and binary files.

Threats considered

  • Cross-account access and insecure direct object references.
  • Malicious uploads and quota abuse.
  • Session theft, secrets leakage and stored XSS.
  • Orphaned files, partial writes and data loss.
  • Document content leaking into logs and analytics.

Current recommendation: private per-user vault, no sharing, TLS + managed at-rest encryption, no E2EE claim.

End-to-end encryption decision

The service stores ciphertext. Keys stay under user control. This is a design commitment, not a claim that encryption has already shipped.

01 · Encrypt locallyClient
Encrypt file and private metadata before upload.
02 · Store ciphertextPrivate
Server enforces ownership but cannot decrypt document contents.
03 · Recover safelyUser-held
Recovery secret is never transmitted in plaintext; loss of all keys means loss of access.

Human-centered security

  • Explain consequences in plain language before users commit.
  • Reduce repeated warnings and security fatigue.
  • Provide clear encryption, upload and saved states.
  • Keep undo for reversible actions and confirmation for permanent deletion.

Release blockers

  • Select and review a maintained cryptographic library.
  • Test nonce uniqueness, tampering and interrupted uploads.
  • Validate recovery loss and multi-device onboarding.
  • Independent security review before any E2EE claim.
